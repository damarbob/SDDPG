# 0038 - Model Deletion Lifecycle

**Status:** Proposed
**Created:** 2026-08-24

## Context

ADR [`0037`](0037-field-deletion-lifecycle.md) closes by naming an open question and assigning it: *"`deleteModel()` gets easier. It inherits the checkpoint guard, the shared tombstoner, and the severance pattern. It still has to settle its own open question — what happens to `entry_data` rows left carrying a dangling `model_id` — which this ADR does not address."* This is that ADR.

The definition layer can now register a model, rename it, and register, rename, retype, promote, demote and delete its fields. It cannot remove the model. That is the last hole in the surface a UI has to bind to, and unlike the others it is undesigned rather than merely unbuilt: no prior ADR mentions model deletion, and `glossary.md`'s `Model` entry carries no lifecycle at all.

Four findings, measured against a real MySQL 8.0.13 on 2026-08-24 rather than read off the DDL, set the shape.

**There is no key to remove, and no foreign key to lean on.** ADR 0037's purge rewrites `entry_data.fields` and the rows survive. A model deletion has no equivalent move: the unit being destroyed is the row itself. `entry_data.model_id → stardust_models.id` is the canonical *deliberate* logical-only link — `schema_reference` §3 makes it the worked example of a cross-group reference the data plane never foreign-keys, so the write-hot table never takes referential-integrity locks on the registry's behalf. That decision forecloses the one-statement answer. Adding `ON DELETE CASCADE` now would put an InnoDB constraint on the largest table in the engine to serve the rarest operation in it. So the rows come out by application code, in chunks, or not at all.

**The cascade is no longer gated on demoting anything.** Deleting a model whose field holds an `assigned` slot fails with **errno 1451**, naming `fk_slot_assignments_field` — `fk_fields_model` is `ON DELETE CASCADE`, but a cascade is still subject to downstream constraints, and the RESTRICT stops it. That measurement is reproduced here and is unchanged. What has changed since it was taken is `Slot\LiveSlotTombstoner`: it clears `field_id = NULL` *before* flipping `status`, releasing the foreign key inside the transaction. Applied to every field of the model in one severance, the identical DELETE then **succeeds**, `fk_fields_model` cascades away every `stardust_fields` row, and the tombstoned slots survive with `field_id` null and `tombstoned_at` set — correct, sweepable inventory. Measured, not inferred.

**The cascade depends on `field_id IS NULL`, not on the slot being non-live.** A `tombstoned` row that still carries a `field_id` re-breaks the DELETE with the same errno 1451. `schema_reference` §4.4 states `field_id IS NULL` for `status IN ('free','tombstoned')` as an invariant, but nothing in the schema enforces it — it is a convention held up by application code. So does a field created *after* severance: an INSERT onto a severed model succeeds today, `PendingDemandReader`'s exact predicate then returns it as demand, and one reservation re-takes the foreign key. Both were measured, and both fail at the *end* of the purge, when the entries are already destroyed.

**A hard DELETE has two collateral surfaces the field purge never touched.** `entry_slots_page_X.entry_id` **is** a real foreign key with `ON DELETE CASCADE`, so the purge removes the model's extension rows for free — the first time anything in the engine deletes from a page table rather than nullifying a column in one. And `stardust_sync_queue.entry_id` is a logical reference with no FK, so a purged entry's queue row survives and `SyncQueueWorkSource` quarantines it as `missing_entry_data`: a self-inflicted dead-letter row per pending write.

## Decision

**Model deletion is severance now, hard purge later, model row last — and unlike a field deletion, it destroys rows rather than keys.**

`deleteModel(tenantId, modelId)` commits one registry transaction and returns. It does not wait for anything.

1. `stardust_models.deleted_at` is set — a new column.
2. `stardust_fields.deleted_at` is set and `is_filterable` cleared on **every** field of the model, in one UPDATE.
3. Every live slot held by any of those fields is tombstoned by the two-step sequence, releasing the foreign key for all of them at once.
4. Terminal `rename_field_{id}` / `retype_field_{id}` / `delete_field_{id}` checkpoint rows are removed for every field of the model.
5. `stardust_schema_version` is bumped exactly once.
6. A `running` `delete_model_{id}` checkpoint is opened.

From that commit the model and every field it owns are gone from every first-class surface: `listModels()` and `describeModel()` omit the model, reads return nothing, filters against its fields are rejected as unknown, export submission is refused, and **writes to it are refused**.

The Reconciler then drains the checkpoint as a sixth work source, deleting `entry_data` rows for the model in bounded, cursor-checkpointed chunks and deleting the matching `stardust_sync_queue` rows in the same chunk transaction. **The final chunk re-asserts severance, deletes the `stardust_models` row — letting `fk_fields_model` cascade the field rows away — deletes the checkpoint, and bumps the schema version, in one transaction.**

Ten rules are binding on the implementation.

**`stardust_models.deleted_at` is required, and it is not redundant with the field markers.** Six sites need a model-level marker; two of them are individually decisive. A guard built only from field markers has to be spelled *"no field of this model is live"* — which is **true of every brand-new empty model**, and a predicate a fresh model satisfies is not a guard on a statement that hard-deletes rows. And a model with no fields at all is legal: `createModel($tenantId, 'Foo')` with an empty field list registers one, its severance marks zero rows, and the purge's claim query has nothing to join through, leaving the checkpoint permanently unclaimable. The other four are `listModels()`, `describeModel()`, `SchemaBuilder::findModelId()` — the get-or-create data-loss guard, exactly ADR 0037's `findFieldId()` argument one level up — and `ModelRenamer`, which must not let a deleting model's name be moved out from under the name-reuse rule. A seventh reason is the next rule but one. The column is `DATETIME NULL DEFAULT NULL`, added by an idempotent `information_schema.COLUMNS` probe following the `deleted_at` migration ADR 0037 added to `stardust_fields`. It gives `stardust_models` its first nullable column; the table still has no `updated_at`, so `ModelRenamer` still needs no clock.

**Every field of the model carries the same `deleted_at` the field lifecycle uses, and that reuse is the design rather than a convenience.** Every existing field-severance guard fires with **zero new predicates** — the read snapshot, the point-read key strip, the write-path canonicalisation, both `SchemaReader` queries, both `SchemaBuilder` get-or-create guards, both CSV header resolvers, the Watcher's demand reader, the ADR [`0007`](0007-write-availability-over-query-completeness.md) exhaustion reserver, the slot reserver's defence in depth, the search driver's filterability check, and the rename, retype and delete initiators. Compaction and the ADR [`0031`](0031-slot-spread-metric.md) spread sampler exclude them structurally instead, both selecting `status IN ('assigned','ready') AND is_filterable = 1`, which a severed field fails twice. The reuse creates no interference in the other direction: the field-purge work source is driven by `job_name LIKE 'delete_field_%'`, and the field marker is only a filter on its join, so marking N fields opens no field purges.

**`SchemaBuilder` must guard on the *model's* marker, and this is the one place field-level markers are actively unsafe.** A field created *after* severance is not marked, and nothing today stops one being created. Measured: the INSERT succeeds; `PendingDemandReader`'s predicate — `is_filterable = 1 AND deleted_at IS NULL`, with **no model predicate** — then returns the new field, so the Watcher provisions a page for a model being destroyed and the exhaustion path reserves it a slot; and the model DELETE then fails errno 1451, at the final chunk, after earlier chunks have already committed their deletes. This is ADR 0037's `is_filterable` failure arriving through a door field markers cannot close, and it is the strongest argument for the model column: without it the guard cannot be written at all. `findModelId()` gains `deleted_at IS NULL` and the resulting unique-index collision becomes a typed `ModelDeletionInProgressException`; `insertField()` gains an explicit model check ahead of the INSERT, rather than relying on a unique index that only fires for a colliding *name*. Note the message matters as well as the guard — reporting `FieldDeletionInProgressException` for a name on a deleting model tells the caller to wait for a name that is never coming back. Two adjacent surfaces belong behind the same guard for the same "quiet success on a model that no longer exists" reason: `compactModel()`, which otherwise reports a *successful empty plan*, and export submission, which otherwise writes a **zero-column CSV over a shrinking row set** — a correct-looking artifact the consumer keeps and never retries.

**The model row outlives the purge for one column, `tenant_id`, and that predicate is the access path rather than belt-and-braces.** The purge needs strictly less from the registry than the field purge does: it builds no JSON path, and `model_id` is already encoded in `job_name`. `stardust_models.id` is globally unique, so `WHERE model_id = ?` selects exactly the same rows as `WHERE tenant_id = ? AND model_id = ?` and the tenant predicate is provably redundant *for correctness* — which is the shape of the argument ADR [`0029`](0029-liberator-sweep-omits-tenant-predicate.md) accepted for the Liberator. It is nonetheless kept, on two counts. First, measured: both `entry_data` secondary indexes lead on `tenant_id`, and for a model whose rows are not spread uniformly across the primary key — which is every model created after the first — the tenant-scoped chunk query is a **covering** range scan of exactly that model's rows, while dropping the predicate collapses it to a primary-key range scan of the whole table. Index skip scan exists in 8.0.13 and the optimiser did not choose it. On 150,000 rows the difference was 43×, per chunk, growing with the table. Second, the operation is irreversible: every other tenant-scope omission in the engine nullifies or rewrites something ADR [`0013`](0013-json-payload-as-system-of-record.md) lets a reader recover from the payload, and this one does not. **ADR 0029 omits a predicate that was never on the access path; this would omit the leading column of the only usable index. Same principle, opposite conclusion.** Adding `tenant_id` to `backfill_checkpoints` instead was rejected: it inverts ADR 0037's own reasoning for one column's convenience, creates a second source of truth for a value the registry already holds, and still would not supply the `deleted_at IS NOT NULL` integrity predicate the claim query needs.

**`delete_model_{id}` is a fourth disjoint checkpoint namespace, the purge opens exactly one of them, and its `LIKE` pattern is escaped.** All four prefixes are thirteen characters, so all four claim queries share the same `SUBSTRING(job_name, 14)` offset, and `delete_model_%` and `delete_field_%` diverge at the eighth character — disjoint. But `job_name` is **operator-supplied** for Backfill Pump CLI jobs, `_` is a single-character wildcard, and `schema_reference` §5.4's own worked example is `model_42_rebuild`. For ADR 0037 the worst case of a stray match was a spurious `JSON_REMOVE`; here it is an unrecoverable `DELETE`. **The model-purge claim query escapes the underscores and additionally carries `deleted_at IS NOT NULL`, which no operator-named job can satisfy.** The three existing repositories carry the same unescaped pattern and should be corrected in the same change — behaviour-preserving, and it stops a fifth namespace re-arguing it. Severance opens **one** checkpoint, never one per field: N field purges would each scan the same partition rewriting the same rows, and no field purge deletes a model, so the entries would be rewritten N times and still be there. Terminal sibling rows are removed for every field and all three job names — the third is new relative to ADR 0037 and is reachable, because a purge manually marked `failed` leaves its row behind — scoped by exact `job_name`, never a `LIKE`. Without that the cascade orphans them: both sibling repositories recover the field id by inner join on a substring of `job_name`, so a row whose field was cascaded away is permanently unclaimable and permanently counted.

**The final chunk re-asserts severance immediately before the model DELETE, and this is a deliberate departure from ADR 0037.** ADR 0037's final chunk trusts that nothing re-slotted the field, and can afford to: if it is wrong, one row survives and one checkpoint is stranded. Here, if it is wrong, the transaction throws errno 1451 **after every earlier chunk has already committed its deletes** — the entries are gone, the registry is intact, the chunk fetch now returns nothing so every tick believes it is the final chunk, and the work source rethrows forever. That is a poison pill hot-looping on top of destroyed data. There is no dead-letter route out of it and there must not be: ADR [`0018`](0018-reconciler-poison-pill-semantics.md)'s quarantine means "commit the survivors and set this one aside", and setting aside a model-purge row means leaving an `entry_data` row with a dangling `model_id` — the exact orphan this ADR exists to eliminate. **The model purge therefore has no DLQ path, by design**, and that is precisely why its last transaction must not be able to fail on a preventable condition. The re-assertion is an idempotent sweep bounded by field count: clear `field_id` on any slot row still referencing one of the model's fields, tombstone it, re-mark any field row that has reacquired a live state. Tens of rows, a no-op in the healthy case, and the difference between a recoverable state and an unrecoverable one.

**`stardust_sync_queue` rows die in the same chunk transaction as their entries, and that requires an index the table does not have.** Leaving them is not an option: the queue row outlives its entry, `SyncQueueWorkSource` fails to find `entry_data`, and the purge manufactures dead-letter rows in proportion to pending writes. But `stardust_sync_queue` carries a primary key and nothing else — deliberately, deferring indexes to "a separate, reviewable schema change". Measured, that deferral now bites: deleting ten rows by `entry_id` is a full table scan taking **100,261 exclusive record locks** on a 100,000-row queue, held for the length of a chunk transaction that also holds the `entry_data` deletes and their page cascade. `SyncQueueWorkSource` claims with `SKIP LOCKED` and steps aside, but `EntryWriter`'s exhaustion enqueue does not — and a blocked sync-queue INSERT is a blocked `write()`, an ADR 0007 write-availability regression caused by a definition-layer operation. **This change adds `INDEX (entry_id)` to `stardust_sync_queue`, behind the same idempotent probe pattern, as a prerequisite rather than a nicety**; measured, it takes the same delete to 30 locks. The delete binds the chunk's ids as literals: expressed as a subquery it reverts to the full scan. It must not be moved outside the chunk transaction — a crash between the two leaves exactly the orphan it exists to prevent.

**Writes to a deleting model are refused, and the inversion of ADR 0037's most easily-mistaken rule is the point.** ADR 0037 *strips* a deleted field's key from an inbound write rather than rejecting it, because a rejected write loses data while a strip converges. For a model there is no residual valid entry to preserve: the write is a request to create a row in a partition being erased. Accepting it either lands behind the cursor, making the acceptance a lie, or ahead of it, creating a **permanent orphan with a dangling `model_id`** — this ADR's whole subject, reintroduced through the one surface ADR 0037 taught us not to leave open. It is also the single case where loud rejection costs the caller nothing real, since the row would be destroyed inside the drain window regardless. So `write()` and `updateEntry()` throw `ModelDeletionInProgressException`; `submitBulkWrite()` refuses at submission; `deleteEntry()` returns `false`, matching its existing idempotent posture, because soft-deleting a row about to be hard-deleted achieves nothing; and `read()`, `search()` and `get()` go dark, indistinguishable from a model that never existed, matching the tenant-isolation posture `describeModel()` already takes. One implementation trap is worth pinning: the read and write snapshots both drive off `stardust_fields WHERE model_id = ?` and neither joins `stardust_models`, so for a **fieldless** model they return zero rows — indistinguishable from a deleting one. Carrying the model flag means making `stardust_models` the driving table with an outer join to `stardust_fields`, not adding an inner join. The snapshot is cached per model and version and severance bumps the version, so the flag propagates immediately.

**A model deletion is refused while any field of it has a lifecycle in flight; it does not cancel one.** Checked in the fixed **rename → retype → delete** order ADR 0036 and ADR 0037 established, now spanning every field of the model. Refusal for ADR 0037's reason, amplified by breadth: cascading a field row away strands a `running` checkpoint no worker can claim and no dashboard can explain, and a model deletion would do it N times. Subsuming an in-flight *field* delete was considered — it is the one sibling that could be cancelled safely, since its only job is removing a key from payloads the model purge will delete outright, and its checkpoint row is removed rather than left running — and rejected for uniformity: one guard, one order, one exception, and the cost of waiting is bounded by a purge the operator can simply let finish. It is recorded because the asymmetry is noticeable and the next reader should find it already argued. Separately, `ux_models_tenant_name` is unconditional, so **the model name is not reusable until the purge lands**; freeing it at initiation would mean renaming the model to a sentinel, and `stardust_models` has no `previous_name` and needs none.

**A purge chunk retries lock-wait timeouts, which is a failure mode ADR 0009's budget does not cover.** The purge and the Liberator now contend for the same `entry_slots_page_X` rows — the purge deleting them by cascade, the Liberator nullifying a tombstoned column across them. Measured in both directions, the loser gets **errno 1205, a lock wait timeout, not errno 1213**; there was no deadlock. That distinction is load-bearing, because the Liberator's ADR [`0009`](0009-tombstone-based-slot-eviction.md) retry path tests for `SQLSTATE 40001` and errno 1213 only, so a 1205 propagates out past the gap path. A lock-wait timeout is the more benign of the two — the transaction rolls back whole and the chunk is safely retryable from the same cursor — but nothing currently retries it on either side. **The model purge must treat 1205 as retryable on the same bounded budget it gives 1213**, and the Liberator's identical exposure is recorded here as a defect to fix separately rather than folded into this change.

### What is deliberately not bridged

**Dead-letter rows naming the model survive it**, by construction — `schema_reference` §5.3 requires the DLQ to outlive `entry_data` row deletion, and ADR 0018 depends on that. Replaying one after a purge is a dead end rather than a loop: the replayer re-enqueues, the executor finds no entry, and the operator gets a fresh `missing_entry_data` row. Worth stating, because it is discoverable the hard way.

**Export and import jobs already in flight are not cancelled.** Submission is refused, but a claimed export job produces a zero-column artifact over a shrinking row set, and import entries targeting the model fail the write guard and land in the DLQ — loud and safe, but not pretty. Failing another daemon's claimed rows from a registry transaction would reach across a concern boundary that ADR [`0015`](0015-database-as-sole-daemon-coordination-point.md)'s coordination model keeps closed. **Persisted export filters** naming the model's fields are stranded harder than a rename strands them, and **Backfill Pump jobs** named after the model are not cleaned up.

**A raw `entry_data` dump mid-purge shows a partially deleted model**, and **the JSON export artifact carve-out inverts** relative to ADR 0037: there, the artifact shows a residual key the API has stopped serving; here it shows nothing at all, because the header resolver returns an empty column set from the moment severance commits.

Finally, what is explicitly **not** an orphan, so that nobody fixes it: the model's tombstoned slot rows are correct and sweepable. The Liberator keys on `status`, `page_id` and `slot_column` and never joins `stardust_fields`, so it reclaims them with the field rows already cascaded away — measured, and the reason ADR 0029's design makes it safe.

### Relationship to prior ADRs

No `Accepted` ADR is amended. ADR 0037 is extended rather than amended: it named this open question, and this ADR answers it while deliberately inverting exactly two of its rules — writes are refused rather than stripped, and the final chunk re-asserts severance rather than trusting it. ADR 0029 is cited and *distinguished*, not followed. ADR 0013 and ADR [`0036`](0036-entry-payload-keys-are-field-names.md) are untouched: the payload is never rewritten by this lifecycle, so the key-format question does not arise. ADR 0009 and ADR [`0017`](0017-schema-registry-as-coordination-contract.md) are untouched — `assigned → tombstoned : field deleted` already covers this, N times in one commit — though ADR 0009's retry budget is recorded above as incomplete for a failure mode this ADR introduces. ADR 0018 is refined by the negative claim that the purge has no dead-letter path. ADR [`0012`](0012-immutable-extension-page-ddl.md) is untouched: deletion never alters page DDL, although this is the first operation to *delete rows from* a page table rather than nullify a column in one. ADR [`0020`](0020-structured-logging-mandate.md) is amended in place — it is `Proposed` — to add `model_delete_started` and `model_delete_complete` to the `registry` vocabulary and `model_delete_purge` to the reconciler's queue discriminator.

## Consequences

**This is the first physical deletion of `entry_data` rows in the engine, and it contradicts the glossary's "Soft Deletion" entry as written.** That entry says entries are never physically removed via `DELETE`. After this ADR it is false, and false in the sharpest available way: the chunk query carries no `deleted_at IS NULL` predicate, matching the rename and retype drains, so entries an operator has already soft-deleted are hard-deleted too. The amendment is a **scoping rather than a retraction** — soft deletion is a property of the *entry* lifecycle, not a promise that bytes are never freed, and the one operation that physically removes entry rows is a definition-layer operation that destroys the model those entries were instances of.

**There is no undelete, and the stakes are a category above ADR 0037's.** There, a definition was gone. Here the data is gone: entries, extension rows, queue rows, field definitions, the model. Nothing in the engine retains a copy and no dead-letter row catches a chunk. The operational obligation is *export before delete*, and the engine neither enforces nor should enforce it — enforcing it would make the definition layer depend on the Chronicler.

**"Severed but unpurged" is a worse resting state than ADR 0037's.** For a field it is a dead key in a payload. For a model it is an entire dataset dark to every API surface while still occupying the largest table in the engine. It remains safe rather than corrupt — the state is fully described by two `deleted_at` columns and one checkpoint row, and re-issuing the delete resumes rather than crashes — but `deleteModel()` returns before anything has been deleted, and the API documentation has to say so in those words.

**A model purge is the most expensive operation in the engine, and it is unbounded.** A rename or field purge issues one JSON mutation per row; this issues a delete that writes undo and redo, cascades into every page table the model touches, and contends with the Liberator over the same rows. Nothing caps the number of entries and no pre-flight refuses a model with a hundred million of them. Nor is disk returned to the filesystem: InnoDB frees pages back to the tablespace, so an operator watching `df` after a large purge sees nothing move. Both belong in a runbook.

**The model name is not reusable until the purge lands, and this costs more than the field-name window.** `defineModel()` is what every seed script calls, so re-running a seed during a purge now throws where it previously succeeded. It also gives `findModelId()` a third behaviour for "the name is not there" — create it, silently create a duplicate because the model was renamed, or throw because it is being deleted. That is one behaviour too many for a get-or-create, and this ADR does not fix it; it notes that the surface is now carrying two known footguns rather than one.

**Two prerequisites land with this change rather than after it.** The `stardust_sync_queue` index is required for correctness of the write path under load, not for the purge's own speed, and `SchemaBuilder`'s model-level guard is required or the purge's last transaction can be made to fail by ordinary use of the definition API. Neither is optional and neither is cosmetic.

**A sixth Reconciler work source is appended, not inserted.** Round-robin order is observable in event streams. Ordering against the three backfill sources is immaterial because the cross-guards make them mutually exclusive per model; ordering against the sync-queue drain is mildly material, since both touch `stardust_sync_queue`, and appending puts the purge last in the tick after the drain has had its turn.

**Deletion is honest.** After `model_delete_complete` the model has no registry row, no fields, no slots, no entries, no extension rows, no queue rows and no checkpoint. Together with ADR 0037 this closes the definition layer: a UI can register, rename, retype, promote, demote, delete and drop.

**One dormant test becomes writable.** `ModelRenamer`'s zero-rows-affected guard has never had a regression test, because nothing in the public API could produce the state. A model that can be deleted between the rename's read and its write produces it, and the test is worth writing when the implementation lands.
